# Studio file protocol

> The rule this exists to enforce: **a finished video lives in exactly one place, under a name
> that says what it is, and you can find it without asking.** Everything else is working files,
> and working files are disposable.

Implemented by `studio/tools/studio-files/files.mjs` (`index` · `collect` · `archive` · `sweep`).

## 1. The one place finished videos live

```
studio/output/
  INDEX.md                                  <- auto-generated catalogue, newest first, FULL paths
  ai-top5/    2026-07-25_ai-top5_hero.mp4
              2026-07-25_ai-top5_spoke.mp4
  yourgov/    2026-07-22_yourgov_4steps-916.mp4
  bridge/     2026-07-25_blue-robot_route-walk.mp4
  splitfire/  2026-07-19_splitfire_advert-v6.mp4
```

**Naming: `YYYY-MM-DD_<project>_<variant>.mp4`**

- date first so a folder listing sorts chronologically on its own
- project second so it groups
- variant last, hyphenated, no spaces, no version noise like `_final_FINAL2`
- one file = one deliverable. Re-renders overwrite the same name unless the *content* differs.

`studio/output/INDEX.md` is regenerated by the tool and is the thing to open when looking for a
video. It lists every deliverable newest-first with its **full Windows path**, ready to paste.

## 2. Everything else is working files

| Kind | Where it lives | Disposable? |
|---|---|---|
| Render scratch | `apps/claude-remotion/out/` | yes, once delivered |
| Preview cuts | `apps/claude-remotion/previews/` | yes |
| Frame sequences | `apps/claude-remotion/public/bridge/*/` | yes — regenerable from the tools |
| Footage triage | `studio/projects/*/{chunks,proxies,candidates,fine}` | yes, after the cut ships |
| Source footage | `studio/projects/*/source`, `_incoming/` | **NO — irreplaceable** |
| Bundle output | `apps/claude-remotion/build/` | yes — `npm run build` regenerates it |
| Records/logs | `studio/projects/*/records`, `studio/logs/` | **NO — provenance** |

Nothing under `studio/output/` is ever a working file, and no working directory is ever the place
you go looking for a finished video.

## 3. Git

`studio/output/` is **gitignored** — videos are never committed (existing repo rule). The INDEX is
gitignored with it; it is a local catalogue, regenerated on demand, not a tracked document.

## 4. Using it

```bash
# rebuild the catalogue (safe, read-only)
node studio/tools/studio-files/files.mjs index

# pull finished videos out of the scattered render dirs into studio/output/
node studio/tools/studio-files/files.mjs collect            # dry run - shows the plan
node studio/tools/studio-files/files.mjs collect --apply

# find reclaimable space
node studio/tools/studio-files/files.mjs sweep              # dry run - reports only
node studio/tools/studio-files/files.mjs sweep --apply --older-than 30
```

**Everything destructive is dry-run by default.** `--apply` is required to move or delete, and
`sweep` never touches source footage, records, logs, or anything under `studio/output/`.

## 5. Getting old files out: archive vs sweep

Two different problems, two different commands. The split matters:

| | `archive` | `sweep` |
|---|---|---|
| Acts on | finished videos in `studio/output/` | regenerable junk (`build/`, frame sequences, scratch) |
| Action | **moves** them to Google Drive | **deletes** them |
| Why | we may want them again; they can't be rebuilt | a command rebuilds them; Drive quota is not for these |

**Archive destination** is a normal folder — Google Drive for desktop mounts your drive locally,
so archiving is just a move and the Drive client uploads it in the background. No API, no tokens.

Resolution order: `--to <dir>` → `$STUDIO_ARCHIVE_DIR` → `%USERPROFILE%\My Drive\project-bright-archive`.

```bash
node studio/tools/studio-files/files.mjs archive --older-than 60           # dry run
node studio/tools/studio-files/files.mjs archive --older-than 60 --apply
```

The archive gets its own `ARCHIVE_INDEX.md` so the Drive folder is self-describing, and
`studio/output/INDEX.md` is rebuilt afterwards so the local catalogue stays true.

**The archive folder lives on the operator's own Drive**, with per-project subfolders and its own
README. It is per-seat: there is no shared folder, and the location is configuration rather than
something this repository can name.

> **Prerequisite for `--apply`:** Google Drive for desktop must be installed and signed in, so the
> local `My Drive\project-bright-archive` is a live synced folder. If `My Drive` is an empty
> placeholder or the Drive client is not running, `archive --apply` refuses — it would otherwise
> write to a local folder that never uploads, which looks exactly like a successful archive.
>
> The Drive *MCP connection* cannot carry the videos: uploads there go as base64 through the
> conversation, so a single 15 MB clip is ~20 MB of text. It is fine for the README and the
> manifest, not for the media. The sync client (or `rclone`) is the transport.

## 6. The rule for new tools

Any tool that produces a finished video writes it to `studio/output/<project>/` with the naming
above, or hands its path to `files.mjs collect`. Tools may use scratch dirs freely — but scratch is
never where a deliverable comes to rest.
